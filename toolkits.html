Toolkits e extensão

O Sabiá cuida do fluxo: o quê, o como e a verificação. O conhecimento da stack, e o padrão de especificação de uma casa, vem de toolkits: pacotes de skills, regras e agentes mantidos fora do Sabiá. Esta página mostra como usar um toolkit, como criar um, os pontos onde o Sabiá aceita extensão e como customizar um fluxo num projeto.

O que é um toolkit

Um toolkit atende um tipo de projeto, uma stack ou uma casa: Java, Spring Batch, Angular, React, o padrão de especificação de uma equipe. Toolkit é skill: o Sabiá não compila conteúdo de toolkit, e fluxo com passos é só do framework. A sa-setup é a única parte do fluxo que sabe procurá-lo. Ela detecta o tipo do projeto e propõe, agente por agente, as skills que vai ligar.

Usar um toolkit

Três passos: instalar na máquina, ligar no projeto e, quando houver versão nova, atualizar.

  1. Instale

    npx sabia toolkits (ou listar, com --json se quiser) mostra os toolkits dos índices, com o autor, a versão do índice, a instalada e a do projeto. Depois, npx sabia toolkits instalar spring-batch (ou spring-batch@1.2.0), ou …instalar <url-git|pasta>[@<ref>][#<subpasta>] para um repositório próprio. #subpasta pega o toolkit dentro de um repositório com vários. Numa pasta local, o @ref lê o toolkit daquele commit, e não da árvore de trabalho. sabia instalar -t spring-batch instala o toolkit junto com o Sabiá.

    O CLI valida o manifesto e o requer antes de gravar. O toolkit vai para ~/.sabia/toolkits/<nome>/, com a origem e o sha em .origem.json. O Kiro lê as skills dali (skill:// no agente); no opencode, elas são copiadas para ~/.config/opencode/skills/. Instalar o mesmo toolkit de outra fonte regrava a origem, mesmo sem mudar o conteúdo.

  2. Ligue no projeto

    Peça "configurar o Sabiá", ou "atualizar a configuração" num projeto já configurado, na sessão padrão. No W5, a setup mostra o inventário por toolkit e marca o detectado com 🔍. No W6, cada um dos 5 agentes recebe um cartão com as skills dos papéis dele já marcadas. A resposta é pelos números: tirar 3,5, pôr 7.

  3. Atualize

    npx sabia toolkits atualizar busca de novo na origem gravada e mostra os arquivos novos, alterados e removidos antes de trocar. Depois, no projeto, "regenerar os agentes". A setup pergunta só sobre as skills novas; a skill que sumiu sai do agente com aviso. Dentro do projeto, sabia toolkits instalar sem argumento instala as versões que ele usa. sabia toolkits remover <nome> avisa quando o projeto ainda usa o toolkit.

Onde a setup procura, nesta ordem

  1. ~/.sabia/toolkits/*/toolkit.json: os que o CLI instalou.
  2. .sabia/toolkits/*/toolkit.json: o toolkit do próprio projeto, versionado com ele.
  3. ~/.kiro/powers/installed/*/toolkit.json: toolkit distribuído como power (sem nenhum ali, ~/.kiro/powers/**/toolkit.json).
  4. Sem manifesto: skills em .kiro/skills/, .opencode/skills/ e .agents/skills/ (no projeto e no home), em ~/.config/opencode/skills/ e nos powers instalados, com metadata.toolkit no front-matter. As skills com o mesmo nome formam um toolkit, mas sem passos nem agentes.
  5. Skills avulsas: entram no inventário geral, e a pessoa decide por agente.

As skills do perfil são fixas: o cartão só mostra os extras. A numeração segue pelas tabelas. No desvio, a skill vem marcada se o toolkit foi detectado; o agente vem sempre desmarcado, porque delegar é escolha da pessoa (agente <n> só vale com a skill ligada).

Criar um toolkit

Um toolkit é uma pasta com um toolkit.json na raiz e os caminhos sempre relativos a ela. Comece no próprio projeto (.sabia/toolkits/<nome>/). Quando ele servir a outros projetos, leve-o para um repositório git e publique no índice.

A estrutura

spring-batch/
├── toolkit.json                 o manifesto (obrigatório)
├── skills/
│   ├── spring-batch-job/
│   │   ├── SKILL.md             a skill: name, description, corpo
│   │   └── references/          o detalhe que ela manda ler
│   ├── spring-batch-teste/SKILL.md
│   └── java/SKILL.md
├── agentes/
│   ├── batch-job.md             prompt do agente neutro
│   └── batch-step.md
└── steering/
    └── batch-regras.md          regras da stack, por papel

Checklist

  • nome em kebab-case e sem o prefixo sa-, mais versao, descricao, tipos-de-projeto e skills.
  • A pasta de cada skill não usa nome do Sabiá (sa-* ou sabia).
  • autor com nome e area: quem fez responde pelo toolkit, e toolkit sem autor é recusado.
  • Todo caminho existe dentro da pasta.
  • O passo aponta para um passo com "desvio": true (hoje, só sa-desenvolver.codificar.tarefa), e o agente está em agentes[].
  • Cada tipo em tipos é desviável no catálogo, e a skill dele traz em papeis o papel de cada dono do passo de desvio. Ver Desvio por tipo.
  • Os itens de rubricas não repetem id do Sabiá nem de outro item.
  • requer.sabia não passa da versão do Sabiá instalado.
  • O agente não tem campo de permissão: quem dá as regras é o papel dono do passo.

O CLI confere tudo isso no sabia toolkits instalar e no atualizar, antes de gravar. O gerador confere de novo na setup e recusa sem gravar nada.

steering[]Regras da stack: o prompt dos agentes dos papéis indicados manda lê-las antes de começar.
comandosProposta para a tabela Comandos do .sabia/sabia.md (compilar, testes, teste do trecho, lint, cobertura, executar) quando o repositório não deixa claro. A pessoa confirma.
verificacaoComo executar os cenários de aceite desse tipo de projeto. Vai ao prompt do sa-verificador.
customizaO toolkit é a cópia modificada de outro. Ver Customizar um toolkit.

Publicar no índice

O índice é um repositório git com .claude-plugin/marketplace.json, e só aponta para os toolkits, que vivem em outro repositório (um por toolkit, ou vários num só, pelo git-subdir). Cada entrada tem name, version, description, autor, o customiza quando houver, e a fonte: um caminho, um repositório github, uma url ou um git-subdir, com ref e sha. O CLI recusa o toolkit se o commit não for o sha. Antes de publicar, teste com npx sabia toolkits instalar <pasta>@<ref>: o CLI lê o toolkit daquele commit e o valida antes de gravar.

O índice público é o dxaraujo/sabia-toolkits. Para um índice próprio, passe --indice <url-git|pasta> ou ponha a URL em ~/.sabia/indices.json. Estar no índice não é auditoria: quem instala decide se confia.

No índice público

  • java 1.1.0: Java 17 com Spring, Lombok, JPA, MapStruct e testes.
  • spring-batch 1.2.0: job, step, reader, processor, writer, tasklet, testes e o agente spring-batch-job.
  • spring-batch-pab 1.3.0: cópia customizada do spring-batch 1.2.0.

Toolkit sem manifesto

Para começar rápido, basta uma skill comum com metadata.toolkit: minha-stack (e, se quiser, metadata.papeis e metadata.tipos-de-projeto) no front-matter, em .kiro/skills/, .opencode/skills/, .agents/skills/ ou ~/.config/opencode/skills/. A setup a mostra agrupada pelo toolkit. Passos, tipos e agentes, porém, só existem com o toolkit.json.

Pontos de extensão

Todo ponto de extensão entra pelos agentes do projeto, nunca pela skill compilada. Há duas origens: o toolkit, que é reaproveitado entre projetos, e o próprio projeto, que vale só nele.

① Skill de apoio

skills[].papeis

A skill vai ao agente dos papéis indicados, que a carrega quando o artefato pede. Exemplo: java para o desenvolvedor, o revisor e o pesquisador.

② Desvio de passo

skills[].passo.passo

A skill (ou um agente dela) assume um passo do Sabiá. Hoje, só em sa-desenvolver.codificar.tarefa. Detalhe.

③ Desvio por tipo

tipos

A skill do toolkit, com o fluxo e o padrão do tipo, escreve um tipo desviável do catálogo (HF, UC, REG, MSG, EL, ET, CT, ATA) no passo de desvio dele. Detalhe.

④ Agente neutro

agentes[]

Vira subagente do dono do passo (<toolkit>-<agente> no Kiro e no opencode), com as regras do papel dele, nunca mais que isso. Pode ter subagentes próprios, que herdam o mesmo papel.

⑤ Steering da stack

steering[]

Regras da stack ligadas aos agentes dos papéis indicados, como "nunca commit dentro de um step".

⑥ Itens de rubrica

rubricas

Itens que se somam à rubrica do sa-revisor, com a severidade de cada um. O toolkit não troca nem afrouxa item do Sabiá.

⑦ Comandos e verificação

comandos · verificacao

A proposta de compilar, testar, lint e cobertura para a tabela Comandos do .sabia/sabia.md, base do backpressure, e o jeito de verificar o aceite, no prompt do sa-verificador.

⑧ Cópia customizada

customiza

Um toolkit derivado de outro para uma casa ou um projeto, completo por si e com as mudanças declaradas. Detalhe.

⑨ Trocar ou inserir um passo

.sabia/fluxo/

O projeto troca o corpo de um passo ou insere um passo novo depois de outro. O dono do fluxo recebe o delta. Detalhe.

⑩ Remover um passo

"remover": [...]

Só passo marcado como removivel no mestre e sem trava. Com trava, a setup diz qual trava o prende e oferece trocar o passo.

⑪ Trocar um padrão

.sabia/padrao/

O formato de um artefato (PRD, ficha, status.md) neste projeto. Vale para todos os agentes, porque o padrão é citado por fluxos de vários donos. O de um tipo do catálogo, .sabia/padrao/requisitos/padrao-<tipo>.md, vale sobre o padrão em vigor do tipo: o do Sabiá ou o do toolkit que o desvia. Detalhe.

⑫ Regras aprendidas

.sabia/sabia.md

Na review da sprint, a curadoria das Lições escolhe o que vira regra no sabia.md. A setup refaz o arquivo e preserva essa seção.

Desvio de passo

O desvio é o ponto mais forte: uma skill de toolkit faz o trabalho de um passo do Sabiá. Mesmo assim, o Sabiá continua dono da revisão, do aceite, do passo validar e do commit.

O que o gerador escreve no prompt do dono

Desvios de toolkit no passo `sa-desenvolver.codificar.tarefa`
(⇢ na tabela do fluxo): o que casa vai ao toolkit, sem perguntar
à pessoa e sem marcar no `status.md` nem no `tasks.md`:
`tarefa que cria ou altera um job ou step` (arquivos
`**/*JobConfig.java`) → delegue ao subagente `batch-job`, com o briefing e o
contrato do `references/passos.md` da skill `sabia`.

Sem agente no manifesto, a linha diz "carregue a skill <skill> e faça o passo por ela". A tabela Desvios de toolkit do sabia.md repete a regra para a sessão sem agente.

Regras do desvio

  • Só vale em passo com "desvio": true no mestre: hoje, só o sa-desenvolver.codificar.tarefa. Com passo inexistente ou sem desvio, o CLI e o gerador recusam. O passo que cria um tipo do catálogo vai por tipos, não por passo.
  • O dono do fluxo, o sa-desenvolvedor, é quem recebe o desvio. Ligado, ele vai no agentes.json (toolkits e passos).
  • para e arquivos vão juntos: basta casar um dos dois.
  • O agente do toolkit ganha as regras do papel dono, as skills e os MCPs ligados ao dono (de outros toolkits, como o java, e do projeto), mas não os subagentes.
  • O briefing e o contrato do passo estão no passos.md da skill sabia.
  • sabia rota src/batch/CargaJobConfig.java mostra por qual passo o arquivo passa e qual toolkit o assume; sabia rota <tasks.md>#2 faz o mesmo pelos arquivos que a tarefa cita.

Desvio por tipo

Um toolkit também pode escrever um tipo do catálogo no formato de uma casa. O toolkit é skill: a skill dele, com o fluxo e o padrão do tipo, escreve o artefato no passo de desvio do tipo e volta ao passo. O catálogo, a revisão, a aprovação e a publicação continuam do Sabiá.

A estrutura

casa/
├── toolkit.json                    "tipos", "rubricas", "requer"
├── skills/casa/SKILL.md            a skill, copiada como está
├── fluxo/fluxo-hf.md               fluxo do tipo HF, lido pela skill
└── padrao/requisitos/padrao-hf.md  padrão do tipo HF, idem
{
  "nome": "casa", "versao": "1.0.0",
  "skills": [{ "caminho": "skills/casa/SKILL.md",
               "papeis": ["especificador", "desenvolvedor"] }],
  "tipos": {
    "HF": { "skill": "skills/casa/SKILL.md",
            "fluxo": "fluxo/fluxo-hf.md",
            "padrao": "padrao/requisitos/padrao-hf.md" },
    "ET": { "skill": "skills/casa/SKILL.md" } },
  "rubricas": [{ "id": "CA1", "tipo": "HF",
    "verificacao": "Toda HF cita o campo de origem",
    "severidade": "IMPORTANTE" }],
  "requer": { "sabia": "2.1.6" },
  …
}

O fluxo e o padrão são opcionais. Só com {"skill": …}, como a ET acima, a skill segue as references dela. O padrão do toolkit segue o nome do Sabiá: padrao/requisitos/padrao-<tipo>.md. A skill traz especificador pela HF e desenvolvedor pela ET.

Os tipos desviáveis do catálogo

TipoPasso de desvioDonoPapel na skill
HF · UC · REG · MSG · ELsa-prd.prd.escrever e sa-especificar.elm.editarsa-especificadorespecificador ou produto
ATAsa-especificar.reuniao.escreversa-especificadorespecificador ou produto
ETsa-desenvolver.codificar.as-builtsa-desenvolvedordesenvolvedor
CTsa-verificar.verificar.casossa-verificadorverificador
GLnão desvia——

A fonte é a coluna desviavel do fluxo/tipos.json. Nos outros passos que criam o tipo, ele é sempre do Sabiá: o CT escrito no detalhamento (sa-refinar.detalhar.cenarios), por exemplo, usa o padrão do Sabiá.

Regras

  • A sigla é do catálogo, desviável e não pendente. O toolkit não cria tipo nem troca padrão do Sabiá: o tipo que não vai por tipos, e o tipo fora do passo de desvio, usam o padrão do Sabiá.
  • A skill está em skills[] e traz em papeis o papel de cada dono do passo de desvio (tabela acima). Sem ele, o CLI e o gerador recusam o toolkit e dizem o papel que falta.
  • A setup pergunta uma vez, no W5: um toolkit de tipo por linha, marcado o detectado e desmarcado o sugerido (toolkit <n>: sim liga). Ligado, sem pergunta por agente, o gerador liga a skill ao dono e põe no prompt dele a linha Tipos com skill de toolkit. A seção de mesmo nome no sabia.md vale na sessão sem agente.
  • O artefato sai no formato do Sabiá: o arquivo pela coluna Arquivo do catálogo; no arquivo de elm/, o frontmatter type · title · status · sources e o corpo sem título Markdown; no bloco do prd.md, o mesmo corpo, sem frontmatter.
  • Os itens de rubrica se somam à rubrica do sa-revisor. Id de um item do Sabiá é recusado; os itens do Sabiá valem igual no que a skill escreve.
  • Dois toolkits do projeto no mesmo tipo ou no mesmo id de rubrica: o gerador recusa e não grava nada.
  • O Sabiá não confere os links dentro dos arquivos do toolkit: um link quebrado só aparece quando o agente o lê.
  • sabia rota --fluxo sa-prd.prd mostra a linha tipo ⇢ escrever: HF → skill casa (fluxo/fluxo-hf.md) toolkit casa 1.0.0.

O padrão do tipo no projeto

A cópia em .sabia/padrao/requisitos/padrao-<tipo>.md vale sobre o padrão em vigor do tipo: o do toolkit que o desvia ou, sem toolkit, o do Sabiá. A base é o sha do padrão de onde a cópia saiu, que a setup calcula pelo --base do gerador.

# tipo desviado pelo toolkit casa
gerar_agentes.py --base ~/.sabia/toolkits/casa/padrao/requisitos/padrao-hf.md
# tipo do Sabiá
gerar_agentes.py --base requisitos/padrao-hf.md

# .sabia/padrao/requisitos/padrao-hf.md
---
{"base": "<saída do --base>"}
---
o padrão copiado, editado pelo projeto

Como fica valendo

  • Tipo do toolkit: a linha Tipos com skill de toolkit do prompt do dono aponta para a cópia, no lugar do padrão do toolkit.
  • Tipo do Sabiá: a skill compilada abre a cópia do projeto antes do padrão dela, e o delta vai ao prompt de todos os agentes.
  • Base que já não bate (o toolkit ou o Sabiá mudou o padrão): ⚠️ no C4, e a setup oferece fundir à mão.
  • Pela sa-setup: "trocar o padrão da HF", na sessão padrão.

Customizar um fluxo no projeto

Pela sa-setup, em linguagem natural, na sessão padrão: "customizar o passo tarefa da sa-desenvolver.codificar", "customizar a review", "trocar o padrão do PRD", "trocar o padrão da HF", "o que este projeto mudou?", "descustomizar…". Nenhum agente sa-* escreve .sabia/fluxo/ nem .sabia/padrao/.

  1. C1 · Achar o pontopelo "quando" dos fluxos e o resumo dos passos; mostra a tabela com o ponto marcadoskill.fluxo.passo
  2. C2 · Escolher a formatrocar · inserir depois de · remover · trocar um padrão (do Sabiá ou de um tipo)removivel
  3. Copiaro corpo compilado (ou o padrão do toolkit) + a base (sha do original, pelo gerador)--base <id>
  4. Editara pessoa edita; as travas continuam valendo.sabia/fluxo/
  5. C3 · Regenerarvalida, mostra o diff do override e dos agentes; "ok" grava--gravar
  6. C4 · O que mudou?o diff de cada override contra o originalW5-F

Exemplo: trocar o rito da review e inserir métricas

.sabia/fluxo/sa-planejamento/review/
├── review.md            só as operações do mestre
└── passos/
    ├── rito.md          trocado: a cópia editada
    └── metricas.md      inserido depois do rito

# review.md
---
{"inserir": [{"id": "metricas", "depois": "rito"}]}
---

# passos/rito.md
---
{"base": "01a888f0593d"}
---
_Rito da review: … a demonstração curta de 10 minutos…_
## Entrada …  ## Faça …  ## Saída …  ## Pare se …

# passos/metricas.md
---
{"resumo": "Métricas da sprint — vazão, tempo médio de
 ciclo e retrabalho — gravadas na seção Review."}
---
## Entrada
O passo rito concluído (o retorno do P.O. registrado).
## Faça …

Como fica valendo

  • O sa-especificador, dono do fluxo review, recebe no prompt só o delta: o passo inserido e o passo trocado.
  • Em cada passo, a skill compilada manda abrir antes o arquivo do projeto. Se ele existe, vale o dele.
  • Fora do agente dono, os passos inseridos e removidos não entram, e o SKILL.md avisa isso. Os desvios valem pelas seções Desvios de toolkit e Tipos com skill de toolkit do sabia.md.
  • sabia rota --fluxo sa-planejamento.review mostra rito com origem "projeto (base …)" e metricas como "inserido depois de rito".

O que o gerador recusa

  • Override órfão, de passo ou padrão que não existe no Sabiá (ou, em requisitos/, no toolkit que desvia o tipo).
  • Cópia sem base, ou com ## Travas ou ## Desvios no corpo, que são seções geradas.
  • remover de passo sem removivel ou com trava, e qualquer liberar (nenhuma trava se libera).
  • Id inválido, repetido, reservado (grafo) ou que fecha um ciclo nas inserções; passo inserido sem o arquivo.

Quando o Sabiá muda

Depois do sabia atualizar (ou do sabia toolkits atualizar, no padrão de um tipo), uma base que já não bate com o original vira ⚠️ no C4. A setup mostra o que mudou no original e oferece fundir à mão. Depois da fusão, grava a base nova e regenera. Descustomizar apaga o override e regenera os agentes.

Customizar um toolkit

Quando uma casa ou um projeto precisa de outro jeito numa stack, faça uma cópia modificada do toolkit. A cópia é completa por si e não herda nada da base: a base só aparece no campo customiza.

{
  "nome": "spring-batch-casa", "versao": "1.0.0",
  "autor": { "nome": "<quem mantém a cópia>", "area": "<equipe>" },
  "customiza": {
    "toolkit": "spring-batch", "versao": "1.2.0",
    "mudancas": ["writer padrão por stored procedure",
                 "skill casa-auditoria nos steps"]
  },
  …
}
  • Mesmos nomes: a cópia mantém os nomes de skill, de agente e de reference da base. O que só ela tem leva prefixo próprio (casa-*.md).
  • Um ou o outro: a cópia substitui a base, e o CLI recusa instalar as duas. A setup propõe a cópia e mostra a base como ↳ substituído por spring-batch-casa.
  • Base mais nova: quando a base tem versão mais nova que a do customiza, o sabia toolkits listar e o W5 mostram ⚠️ "a base mudou desde a cópia". Quem mantém a cópia decide o que trazer.
Toolkit customiza a stack para vários projetos. Override de fluxo customiza o processo de um projeto. Antes de copiar um toolkit para mudar um passo do Sabiá, veja se o caso não é um override.
