Toolkits e extensão

O Sabiá cuida do fluxo: o quê, o como e a verificação. O conhecimento da stack, e o padrão de especificação de uma casa, vem de toolkits: pacotes de skills, regras e agentes mantidos fora do Sabiá. Esta página mostra como usar um toolkit, como criar um, os pontos onde o Sabiá aceita extensão e como customizar um fluxo num projeto.

O que é um toolkit

Um toolkit atende um tipo de projeto, uma stack ou uma casa: Java, Spring Batch, Angular, React, o padrão de especificação de uma equipe. Toolkit é skill: o Sabiá não compila conteúdo de toolkit, e fluxo com passos é só do framework. A sa-setup é a única parte do fluxo que sabe procurá-lo. Ela detecta o tipo do projeto e propõe, agente por agente, as skills que vai ligar.

Usar um toolkit

Três passos: instalar na máquina, ligar no projeto e, quando houver versão nova, atualizar.

  1. Instale

    npx sabia@next toolkits listar mostra os toolkits dos índices, com o autor, a versão do índice, a instalada e a do projeto. Depois, npx sabia@next toolkits instalar spring-batch, ou …instalar <url-git|pasta>[@<ref>][#<subpasta>] para um repositório próprio. #subpasta pega o toolkit dentro de um repositório com vários. Numa pasta local, o @ref lê o toolkit daquele commit, e não da árvore de trabalho. O toolkit vai para ~/.sabia/toolkits/<nome>/, com a origem e o sha em .origem.json. toolkits baixar só baixa e valida, sem copiar para as ferramentas. Baixar o mesmo toolkit de outra fonte regrava a origem, mesmo sem mudar o conteúdo.

  2. Ligue no projeto

    Peça "configurar o Sabiá", ou "atualizar os agentes do Sabiá" num projeto já configurado. No W5, a setup mostra o inventário por toolkit e marca o detectado com 🔍. No W6, cada agente recebe um cartão com as skills dos papéis dele já marcadas. A resposta é pelos números: tirar 3,5, pôr 7.

  3. Atualize

    npx sabia@next toolkits atualizar busca de novo na origem gravada e mostra os arquivos novos, alterados e removidos antes de trocar. Depois, no projeto, "atualizar os agentes do Sabiá". A setup pergunta só sobre as skills novas; a skill que sumiu sai do agente com aviso. Dentro do projeto, sabia toolkits instalar sem argumento instala as versões que ele usa. sabia toolkits remover <nome> avisa quando o projeto ainda usa o toolkit.

Onde a setup procura, nesta ordem

  1. ~/.sabia/toolkits/*/toolkit.json: os que o CLI instalou.
  2. .sabia/toolkits/*/toolkit.json: o toolkit do próprio projeto, versionado com ele.
  3. ~/.kiro/powers/installed/*/toolkit.json: toolkit distribuído como power.
  4. Sem manifesto: skills em .kiro/skills/, .opencode/skills/ e .agents/skills/ (no projeto e no home), em ~/.config/opencode/skills/ e nos powers instalados, com metadata.toolkit no front-matter. As skills com o mesmo nome formam um toolkit, mas sem passos nem agentes.
  5. Skills avulsas: entram no inventário geral, e a pessoa decide por agente.

O cartão do W6, para o sa-desenvolvedor

      #  Skill                Para quê · origem
 [✅] 1  java                 Java 17, testes e padrões
                              · toolkit java 🔍
 [✅] 2  spring-batch-job     steps chunk/tasklet

                              · toolkit spring-batch 🔍

A numeração segue pelas tabelas. No desvio, a skill vem marcada se o toolkit foi detectado; o agente vem sempre desmarcado, porque delegar é escolha da pessoa.

Criar um toolkit

Um toolkit é uma pasta com um toolkit.json na raiz e os caminhos sempre relativos a ela. Comece no próprio projeto (.sabia/toolkits/<nome>/). Quando ele servir a outros projetos, leve-o para um repositório git e publique no índice.

A estrutura

spring-batch/
├── toolkit.json                 o manifesto (obrigatório)
├── skills/
│   ├── spring-batch-job/
│   │   ├── SKILL.md             a skill: name, description, corpo
│   │   └── references/          o detalhe que ela manda ler
│   ├── spring-batch-teste/SKILL.md
│   └── java/SKILL.md
├── agentes/
│   ├── batch-job.md             prompt do agente neutro
│   └── batch-step.md
└── steering/
    └── batch-regras.md          regras da stack, por papel

Checklist

  • nome em kebab-case e sem o prefixo sa-, mais versao, descricao, tipos-de-projeto e skills.
  • A pasta de cada skill não usa nome do Sabiá (sa-* ou sabia).
  • autor com nome e area: quem fez responde pelo toolkit, e toolkit sem autor é recusado.
  • Todo caminho existe dentro da pasta.
  • O passo aponta para um passo com "desvio": true (hoje, só sa-codificar.codificar.tarefa), e o agente está em agentes[].
  • Cada tipo em tipos é desviável no catálogo, e a skill dele traz em papeis o papel de cada dono do passo de desvio. Ver Desvio por tipo.
  • requer.sabia não passa da versão do Sabiá instalado.
  • O agente não tem campo de permissão: quem dá as regras é o papel dono do passo.

O CLI confere tudo isso no sabia toolkits baixar e no instalar. O gerador confere de novo na setup e recusa sem gravar nada.

O manifesto

{
  "$schema": "https://raw.githubusercontent.com/dxaraujo/sabia/main/skills/sa-setup/assets/toolkit.schema.json",
  "nome": "spring-batch", "versao": "1.0.0",
  "autor": { "nome": "<quem fez>", "area": "<equipe>" },
  "descricao": "Jobs Spring Batch 5: steps chunk e tasklet…",
  "tipos-de-projeto": ["batch"],
  "deteccao": { "arquivos": ["pom.xml", "build.gradle"],
                "contem": ["spring-batch-core"] },
  "skills": [
    { "caminho": "skills/spring-batch-job/SKILL.md",
      "papeis": ["desenvolvedor", "revisor"],
      "passo": { "passo": "sa-codificar.codificar.tarefa",
                 "para": "tarefa que cria ou altera um job ou step",
                 "arquivos": ["**/*JobConfig.java"],
                 "agente": "batch-job" } },
    { "caminho": "skills/spring-batch-teste/SKILL.md",
      "papeis": ["desenvolvedor", "verificador"] }
  ],
  "steering": [ { "caminho": "steering/batch-regras.md",
                  "papeis": ["desenvolvedor", "revisor"] } ],
  "comandos": { "compilar": "mvn -q -DskipTests compile",
                "testes": "mvn -q test",
                "teste-unico": "mvn -q -Dtest={alvo} test" },
  "verificacao": "Executar o job pelo teste de integração…",
  "agentes": [
    { "nome": "batch-job", "descricao": "Codifica um job…",
      "prompt": "agentes/batch-job.md",
      "skills": ["skills/spring-batch-job/SKILL.md"],
      "subagentes": ["batch-step"] }
  ]
}

skills[].papeisQuem recebe a skill: produto, especificador, pesquisador, desenvolvedor, revisor, verificador, orquestrador.

Publicar no índice

O índice é um repositório git com .claude-plugin/marketplace.json, e só aponta para os toolkits: cada um vive no repositório dele. Cada entrada tem name, version, description, autor, o customiza quando houver, e a fonte: um caminho, um repositório github, uma url ou um git-subdir, com ref e sha. O CLI recusa o toolkit se o commit não for o sha. Confira antes com npx sabia@next toolkits baixar <url-git>@<ref>.

O índice público é o dxaraujo/sabia-toolkits. Para um índice próprio, passe --indice <url-git|pasta> ou ponha a URL em ~/.sabia/indices.json. Estar no índice não é auditoria: quem instala decide se confia.

No índice público

  • java 1.1.0: Java 17 com Spring, JPA e testes.
  • spring-batch 1.2.0: job, step, reader, writer, testes e o agente spring-batch-job.
  • spring-batch-pab 1.3.0: cópia customizada do spring-batch 1.2.0.
  • iara 0.3.2: padrão de especificação (HF, REG, EL, CT, ET e ATA) sobre o fluxo de especificação do Sabiá.

Toolkit sem manifesto

Para começar rápido, basta uma skill comum com metadata.toolkit: minha-stack (e, se quiser, metadata.papeis e metadata.tipos-de-projeto) no front-matter, em .kiro/skills/, .opencode/skills/ ou .agents/skills/. A setup a mostra agrupada pelo toolkit. Passos, tipos e agentes, porém, só existem com o toolkit.json.

Pontos de extensão

Todo ponto de extensão entra pelos agentes do projeto, nunca pela skill compilada. Há duas origens: o toolkit, que é reaproveitado entre projetos, e o próprio projeto, que vale só nele.

① Skill de apoio

skills[].papeis

A skill vai ao agente dos papéis indicados, que a carrega quando o artefato pede. Exemplo: java para o desenvolvedor, o revisor e o pesquisador.

② Desvio de passo

skills[].passo.passo

A skill (ou um agente dela) assume um passo do Sabiá. Hoje, só em sa-codificar.codificar.tarefa. Detalhe.

③ Desvio por tipo

tipos

A skill do toolkit, com o fluxo e o padrão do tipo, escreve um tipo desviável do catálogo no passo de desvio dele. Detalhe.

④ Agente neutro

agentes[]

Vira subagente do dono do passo, com as regras do papel dele, nunca mais que isso. Pode ter subagentes próprios, que herdam o mesmo papel.

⑤ Steering da stack

steering[]

Regras da stack ligadas aos agentes dos papéis indicados, como "nunca commit dentro de um step".

⑥ Itens de rubrica

rubricas

Itens que se somam à rubrica do revisor, com a severidade de cada um. O toolkit não troca nem afrouxa item do Sabiá.

⑦ Comandos e verificação

comandos · verificacao

A proposta de compilar, testar, lint e cobertura para o sabia.md, que o passo validar roda, e o jeito de verificar o aceite.

⑧ Cópia customizada

customiza

Um toolkit derivado de outro para uma casa ou um projeto, completo por si e com as mudanças declaradas. Detalhe.

⑨ Trocar ou inserir um passo

.sabia/fluxo/

O projeto troca o corpo de um passo ou insere um passo novo depois de outro. O dono do fluxo recebe o delta. Detalhe.

⑩ Remover um passo

"remover": [...]

Só passo marcado como removivel e sem trava. Com trava, a setup diz qual trava o prende e oferece trocar o passo.

⑪ Trocar um padrão

.sabia/padrao/

O formato de um artefato (PRD, ficha, status.md) neste projeto. Vale para todos os agentes, porque o padrão é citado por fluxos de vários donos. Vale só sobre um padrão do Sabiá, não sobre o de um toolkit.

⑫ Regras aprendidas

.sabia/sabia.md

A lição que se repete vira regra no sabia.md, pela sa-aprender. A setup refaz o arquivo e preserva essa seção.

Desvio de passo

O desvio é o ponto mais forte: uma skill de toolkit faz o trabalho de um passo do Sabiá. Mesmo assim, o Sabiá continua dono da revisão, do GATE, do passo validar e do commit.

O que o gerador escreve no prompt do dono

Desvios de toolkit no passo `sa-codificar.codificar.tarefa`
(⇢ na tabela do fluxo): o que casa vai ao toolkit, sem perguntar
à pessoa e sem marcar no `status.md` nem no `tasks.md`:
`tarefa que cria ou altera um job ou step` (arquivos
`**/*JobConfig.java`) → delegue ao subagente `batch-job`, com o briefing e o
contrato do `references/passos.md` da skill `sabia`.

Sem agente no manifesto, a linha diz "carregue a skill <skill> e faça o passo por ela". A tabela Desvios de toolkit do sabia.md repete a regra para a sessão sem agente.

Regras do desvio

  • Só vale em passo com "desvio": true no mestre: hoje, só o sa-codificar.codificar.tarefa. Com passo inexistente ou sem desvio, o CLI e o gerador recusam. O passo que cria um tipo do catálogo vai por tipos, não por passo.
  • O dono do fluxo, o sa-desenvolvedor, é quem recebe o desvio. Ligado, ele vai no agentes.json (toolkits e passos).
  • para e arquivos vão juntos: basta casar um dos dois.
  • O agente do toolkit ganha as regras do papel dono, as skills e os MCPs ligados ao dono (de outros toolkits, como o java, e do projeto), mas não os subagentes.
  • O briefing e o contrato do passo estão no passos.md da skill sabia.
  • sabia rota src/batch/CargaJobConfig.java mostra por qual passo o arquivo passa e qual toolkit o assume.

Desvio por tipo

Um toolkit também pode escrever um tipo do catálogo no formato de uma casa. O toolkit é skill: a skill dele, com o fluxo e o padrão do tipo, escreve o artefato no passo de desvio do tipo e volta ao passo. O catálogo, o envelope OKF, a revisão, o GATE e a publicação continuam do Sabiá.

A estrutura

exemplo/
├── toolkit.json             "tipos", "rubricas", "requer"
├── skills/exemplo/SKILL.md  a skill, copiada como está
├── fluxo/fluxo-hf.md        fluxo do tipo HF, lido pela skill
└── padrao/padrao-hf.md      padrão do tipo HF, idem
{
  "nome": "exemplo", "versao": "1.0.0",
  "skills": [{ "caminho": "skills/exemplo/SKILL.md",
               "papeis": ["especificador"] }],
  "tipos": { "HF": { "skill": "skills/exemplo/SKILL.md",
                    "fluxo": "fluxo/fluxo-hf.md",
                    "padrao": "padrao/padrao-hf.md" } },
  "rubricas": [{ "id": "EX1", "tipo": "HF",
    "verificacao": "Toda HF cita o campo de origem",
    "severidade": "IMPORTANTE" }],
  "requer": { "sabia": "2.0.0" },
  …
}

O fluxo e o padrão são opcionais. Só com {"skill": …}, a skill segue as references dela.

Os tipos desviáveis do catálogo

TipoPasso de desvio
HF · REG · EL · CTsa-prd.prd.escrever e sa-especificar.fatia.escrever
ETsa-prd.prd.escrever e sa-consolidar.consolidar.elm
ATAsa-especificar.reuniao.escrever
GLnão desvia

Nos outros passos que criam o tipo, ele é sempre do Sabiá. A ET as-built escrita no PR, por exemplo, usa o padrão do Sabiá.

Regras

  • A sigla é do catálogo, desviável e não pendente. O toolkit não cria tipo.
  • A skill está em skills[] e traz em papeis o papel de cada dono do passo de desvio (ET: especificador e produto). Sem ele, o CLI e o gerador recusam o toolkit.
  • Sem pergunta por agente: o gerador liga a skill ao dono e põe no prompt dele a linha Tipos com skill de toolkit. A seção de mesmo nome no sabia.md vale na sessão sem agente.
  • O artefato sai no padrão OKF do Sabiá: o arquivo pela coluna Arquivo do catálogo, o envelope e o status que o passo manda.
  • Os itens de rubrica se somam à rubrica do revisor. Id de um item do Sabiá é recusado.
  • Dois toolkits do projeto no mesmo tipo ou no mesmo id de rubrica: o gerador recusa e não grava nada.
  • O Sabiá não confere os links dentro dos arquivos do toolkit: um link quebrado só aparece quando o agente o lê.
  • sabia rota --fluxo sa-prd.prd mostra o tipo com tipo ⇢, a skill e o toolkit.

Customizar um fluxo no projeto

Pela sa-setup, em linguagem natural, na sessão padrão: "quero estender o passo de implementar da sa-codificar", "customizar a review", "trocar o padrão do PRD", "o que este projeto mudou?", "descustomizar…". Nenhum agente sa-* escreve .sabia/fluxo/ nem .sabia/padrao/.

  1. C1 · Achar o pontopelo "quando" dos fluxos e o resumo dos passos; mostra a tabela com o ponto marcadoskill.fluxo.passo
  2. C2 · Escolher a formatrocar · inserir depois de · remover · trocar um padrãoremovivel
  3. Copiaro corpo compilado + a base (sha do original, pelo gerador)--base <id>
  4. Editara pessoa edita; as travas continuam valendo.sabia/fluxo/
  5. C3 · Regenerarvalida, mostra o diff do override e dos agentes; "ok" grava--gravar
  6. C4 · O que mudou?o diff de cada override contra o originalW5-F

Exemplo: trocar o rito da review e inserir métricas

.sabia/fluxo/sa-planejamento/review/
├── review.md            só as operações do mestre
└── passos/
    ├── rito.md          trocado: a cópia editada
    └── metricas.md      inserido depois do rito

# review.md
---
{"inserir": [{"id": "metricas", "depois": "rito"}]}
---

# passos/rito.md
---
{"base": "01a888f0593d"}
---
_Rito da review: … a demonstração curta de 10 minutos…_
## Entrada …  ## Faça …  ## Saída …  ## Pare se …

# passos/metricas.md
---
{"resumo": "Métricas da sprint — vazão, tempo médio de
 ciclo e retrabalho — gravadas na seção Review."}
---
## Entrada
O passo rito concluído (o retorno do P.O. registrado).
## Faça …

Como fica valendo

  • O sa-produto, dono do fluxo review, recebe no prompt só o delta: o passo inserido e o passo trocado.
  • Em cada passo, a skill compilada manda abrir antes o arquivo do projeto. Se ele existe, vale o dele.
  • Fora do agente dono, os passos inseridos e os desvios não entram, e o SKILL.md avisa isso.
  • sabia rota --fluxo sa-planejamento.review mostra rito com origem "projeto (base …)" e metricas como "inserido depois de rito".

O que o gerador recusa

  • Override órfão, de passo ou padrão que não existe no Sabiá.
  • Cópia sem base, ou com ## Travas ou ## Desvios no corpo, que são seções geradas.
  • remover de passo com trava, e qualquer liberar (nenhuma trava se libera).
  • Id inválido, repetido ou que fecha um ciclo nas inserções.

Quando o Sabiá muda

Depois do sabia atualizar, uma base que já não bate com o original vira ⚠️ no C4. A setup mostra o que mudou no original e oferece fundir à mão. Depois da fusão, grava a base nova e regenera. Descustomizar apaga o override e regenera os agentes.

Customizar um toolkit

Quando uma casa ou um projeto precisa de outro jeito numa stack, faça uma cópia modificada do toolkit. A cópia é completa por si e não herda nada da base: a base só aparece no campo customiza.

{
  "nome": "spring-batch-casa", "versao": "1.0.0",
  "autor": { "nome": "<quem mantém a cópia>", "area": "<equipe>" },
  "customiza": {
    "toolkit": "spring-batch", "versao": "1.0.0",
    "mudancas": ["writer padrão por stored procedure",
                 "skill casa-auditoria nos steps"]
  },
  …
}
  • Mesmos nomes: a cópia mantém os nomes de skill, de agente e de reference da base. O que só ela tem leva prefixo próprio (casa-*.md).
  • Um ou o outro: a cópia substitui a base, e o CLI recusa instalar as duas. A setup propõe a cópia e mostra a base como ↳ substituído por spring-batch-casa.
  • Base mais nova: quando a base tem versão mais nova que a do customiza, o sabia toolkits listar e o W5 mostram ⚠️ "a base mudou desde a cópia". Quem mantém a cópia decide o que trazer.
Toolkit customiza a stack para vários projetos. Override de fluxo customiza o processo de um projeto. Antes de copiar um toolkit para mudar um passo do Sabiá, veja se o caso não é um override.
